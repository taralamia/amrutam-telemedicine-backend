# Doctor profile and availability

Doctor accounts are provisioned separately; self-registration cannot create privileged roles. The authenticated doctor creates one profile at `POST /v1/doctors/me/profile`. Profiles are unlisted by default and require later admin approval before public search. `GET /v1/doctors/me/profile` returns the current profile. `PATCH /v1/doctors/me/profile` requires the current profile `version`; successful edits increment it, stale edits return 409, and changing directory identity/details unlists the profile pending review.

Doctors create future, timezone-aware slots at `POST /v1/doctors/me/slots`, list their own slots at `GET /v1/doctors/me/slots`, and toggle availability with `PATCH /v1/doctors/me/slots/{slot_id}` and `{ "version": 1, "available": false }`. This conditional update increments the version, preventing stale writes. A booked/held slot cannot be toggled by the doctor. `DELETE /v1/doctors/me/slots/{slot_id}` soft-deletes only available/unavailable slots with a matching version. All write requests require `Idempotency-Key` and verified MFA; an audit record is committed with each change.

PostgreSQL's GiST exclusion constraint rejects intersecting intervals for the same doctor (half-open `[start,end)` ranges allow adjacent appointments). A database unique constraint also rejects duplicate exact slot definitions. Soft-deleted slots are excluded from overlap enforcement, allowing a replacement schedule. The booking path later uses conditional slot status/version updates on the primary database; Redis locks are not needed for correctness.
